# Static review: v0.22.0 to `chore/finish-plans`

Reviewed 2026-09-26. Baseline: `v0.22.0` (`d126e73b46d1a409fea8f04931a6cf2ef22b0ca2`). Target: `6431ae2a8c99848e3daa4796e44eeebf45f74c7d`. The tag is an ancestor of the target. The comparison contains 125 commits and a net change of 467 files (24,355 insertions and 15,641 deletions). This review considers the net diff, related specs and plans, and the test source. **No tests, builds, or live debugging sessions were run.** Existing local changes to `.claude/settings*.json` were outside this review.

## Verdict

The .NET Framework and multi-targeting feature has been implemented across the Rust host, both sidecars, the VS Code extension, and the Windows test corpus. Every item in `docs/plans/DOTNET-FRAMEWORK-PLAN.md` is checked, and the ten new Windows-only VS Code suites are assigned to test chunks. **It is not yet accurate to sign off the implementation as fully finished against `docs/specs/DOTNET-FRAMEWORK-SPEC.md`.** Two code paths contradict `[NETFX-CONTEXT]`, the Run/F5 path comparison can select the wrong active framework on a case-sensitive filesystem, and an explicit test selection can go green after running zero tests on a non-Windows host. The findings below are source-level conclusions; their runtime frequency is not established without tests.

The spec explicitly excludes debugging the desktop .NET Framework CLR: Debug of a Framework-only target is refused, while Run uses the desktop CLR on Windows. “Finished” must be judged against that stated scope, not against availability of a .NET Framework debugger.

## Findings, in priority order

### [P2] A single-target C# project name can be mistaken for a framework

`src/sidecars/SharpLsp.Sidecar.CSharp/Workspace/TargetFrameworks.cs:17-22` treats *any* final parenthesized suffix in `Project.Name` as a target framework. `ContextsOf` at lines 25-33 then treats that project as a framework context. For a single-target project named `Utility(net48)` that actually targets `net10.0`, `GetTargetFrameworksAsync` in `WorkspaceManager.TargetFrameworks.cs:36-49` can report `active: "net48", available: ["net48"]`; `[NETFX-CONTEXT]` requires `active: null, available: []`. The existing single-target test at `WorkspaceManagerTargetFrameworkTests.cs:123` uses the unambiguous name `Single`, so it cannot catch this. Infer the framework from evaluated project metadata or verified multi-target contexts, and add a real project with a parenthesized name to the sidecar and editor tests.

### [P2] Framework-switch notifications precede the specified invalidation and diagnostics

`src/sharplsp/src/target_framework.rs:114-130` forwards the switch and immediately calls `announce`, which queues `sharplsp/targetFrameworkChanged` and refresh requests. Only **after** `handle_set` returns does `src/sharplsp/src/main.rs:917-930` clear `nav_cache` and call `republish_open_diagnostics`. `[NETFX-CONTEXT]` specifies cache clear, diagnostic republication, change notification, then supported refresh requests. The host end-to-end test in `src/sharplsp/tests/e2e_modules/target_framework.rs:80-112` checks that messages arrive, but not their order relative to diagnostics or cache invalidation. This is a definite ordering mismatch and risks the editor refreshing before the new diagnostics have been published. Move the announcement after invalidation and diagnostic scheduling, and assert the observable ordering in an end-to-end test. Diagnostic work is asynchronous, so a strict “published before announcement” contract also needs explicit synchronization or a clarified spec.

### [P2] Run/F5 compares project paths with the wrong case rule

`src/editors/vscode/src/launch-framework-run.ts:41-43` resolves both paths and lowercases them unconditionally. `chosenFramework` at lines 50-59 uses this comparison to decide whether the focused document's active framework belongs to the selected project. On Linux, two distinct projects whose paths differ only by case compare equal; an explicit project launch while an editor from the other project is focused can borrow that editor's active framework and run or debug the wrong build. The shared `src/editors/vscode/src/paths.ts:86-94,148-150` already implements platform-aware `samePath`, but the new launch code bypasses it. Replace the local comparison with `samePath` and cover the explicit-project, different-editor case on a case-sensitive filesystem. The Windows-only .NET Framework Run/F5 suite does not exercise this case.

### [P2] An explicitly selected Windows-only suite can report success with zero tests

On a non-Windows host, `src/editors/vscode/src/test/suite/index.ts:49-73` first confirms that an explicit `MOCHA_FILES` pattern matches a compiled suite, then removes every `windowsOnly` match. If the pattern names only `netfx-language.test.js`, for example, `resolveSuiteFiles` returns an empty list. `run()` at lines 117-130 registers no Mocha files and resolves successfully when Mocha reports zero failures. This is a **test-execution gate weakness**, even though the CI matrix correctly sends the Framework chunks only to Windows. Make an explicit selection that becomes empty fail with a clear platform reason, or return an explicit skipped-leg verdict rather than a green test result; add a runner-contract test for that case.

## Test-strength audit

No test file was deleted in the net diff. The `test-chunks.json` excluded list remains empty; the ten new Framework VS Code suites are routed to Windows, where desktop CLR execution is possible. The coverage and duplication gates tightened. In the reviewed refactors, `assertContainsAll`/`assertContainsNone` preserve the prior membership checks, and the large context-menu and LSP suites retain their behavior cases through parameterized tests and shared setup. I found **no confirmed assertion weakening intended to make a failing test pass**. However, the explicit-suite path above can make a requested test run pass without executing a test. This is a static conclusion, not a claim that the suites pass.

The three product-code findings identify missing regression cases: a C# single-target project with a parenthesized name, ordered switch notifications/diagnostics, and explicit project Run/F5 with a differently cased focused project on Linux. Their absence limits the “all `[NETFX]` clauses asserted” claim in commit `dd35ecc` and in the checked plan. The existing test at `src/sharplsp/tests/e2e_modules/target_framework.rs:80-112` proves presence of notifications, not the specified ordering.

An older CI risk recorded in `docs/reviews/POST-7C3B1CE-REGRESSION-REVIEW.md` remains visible: `.github/workflows/ci.yml` still skips `detect-changes` for Dependabot, allowing the terminal gate to treat skipped jobs as success. The guard is unchanged since `v0.22.0`, so this is **not** a regression introduced by this range; it remains relevant to release confidence.

## Sign-off boundary

The feature is broad and close to complete, including F# and the real Windows corpus. The checked plan describes work that was written, not proof that every spec case is correct. Resolve the four findings, add their regression assertions, and obtain a Windows CI run before calling the .NET Framework implementation finished and verified. This document deliberately makes no test-pass or regression-free claim because only static analysis was requested.
